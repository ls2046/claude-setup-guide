# 机场＋静态 IP

## 先识别职责

链路是：设备 → 机场节点（中转）→ 静态代理（落地）→ 网站。网站通常看到最终出口；机场影响到落地的连通与速度，落地影响对目标的连接。不能因为 IP 固定就推断速度快、住宅属性、信誉好或不触发验证。

拿到新的代理命令时只提取协议、入口、端口与认证方式，私密保存。先检查供应商支持的协议，不假定同一端口支持 HTTP、HTTPS、SOCKS5 或 UDP；也不要把 `http://` 自动改为 TLS。

## 候选构建

Mihomo 常用 `dialer-proxy` 把静态节点的拨号交给机场组；该字段放在静态 **节点** 上。下例是合并片段，不是可直接接管整机的完整配置，须替换占位符并引用真实存在的上游节点：

```yaml
proxies:
  - name: STATIC-EXIT
    type: http
    server: STATIC_PROXY_HOST
    port: 12345
    username: REPLACE_PRIVATELY
    password: REPLACE_PRIVATELY
    dialer-proxy: STATIC-UPSTREAM
proxy-groups:
  - name: STATIC-UPSTREAM
    type: select
    proxies:
      - EXISTING_AIRPORT_NODE
  - name: STATIC-ROUTE
    type: select
    proxies:
      - STATIC-EXIT
```

按现有规则把授权流量指向 `STATIC-ROUTE`，不直接追加全局 MATCH 覆盖用户原规则。上游组不能包含静态节点本身、引用它的组或会再次选回它的自动组。独立测试核心与日常核心的端口、控制器、缓存和工作目录分开。

供应商明确支持 SOCKS5 时可生成独立 SOCKS5 候选，和 HTTP 在同一上游交替测试后决定。SOCKS5 名称本身不能证明 UDP 可用；HTTP CONNECT 的成功也不证明 UDP/STUN 被静态出口承载。若需要统一出口但落地不支持 UDP，明确限制：在授权范围内阻止受影响流量直连或选择确实支持的方案，不能把 UDP 偷跑机场或本地当作静态出口验收通过。

来源：[Mihomo dialer-proxy](https://wiki.metacubex.one/config/proxies/dialer-proxy/)、[HTTP 节点](https://wiki.metacubex.one/config/proxies/http/)。部署时重新核对安装版本支持的字段，不沿用已废弃 relay 作为通用模板。

## 测试矩阵与选择

交替比较：A 机场单跳，B 同一机场＋静态出口，C 另一个机场＋同一静态出口，D 同上游不同受支持协议。各路径都使用相同目标和大小；改变一项后重测。不能按节点名字的国家或一次延迟最低就选“最优”。

- A 快 B 慢：优先检查落地、上游到落地链路、协议或目标限制。
- B 慢 C 好：更换中转可改善，不需要更换静态出口。先固定胜出中转再观察稳定性。
- 所有路径某站失败：检查该站资源、服务状态或业务返回，不归咎整条线路。
- IP 回显正常但 Google 失败：看 TLS/CONNECT/超时细节与目标域名规则，不推断静态 IP 天生不能连 Google。

用户要求“机场源头不用管”时不改订阅来源，只优化本地规则、落地协议、允许的中转选择并说明供应商瓶颈。

## 持久化与替换

1. 动态定位当前订阅 ID、增强配置/脚本与核心实际生成文件。备份并保留旧增强逻辑，按稳定节点名更新字段，重复执行不重复追加。
2. 新配置先独立测试。支持源文件不等于生成配置正确，对最终生成结果执行核心检查。
3. 热加载后读回 STATIC 节点的服务器/端口、上游选择、规则命中、实际出口；凭据只核对存在与匹配，不打印。
4. 旧连接可能继续旧链路。针对测试目标新建连接或关闭已确认的相关连接，不默认清空所有应用会话。
5. 更新订阅或重新加载后复查增强还在。用户说“不能点更新”时禁止刷新远程订阅，使用已有有效节点及本地增强。
6. 用户要求删除旧静态 IP：先把所有引用切到已测可用替代节点，再删除本次明确替换的旧节点/字段；检查引用完整性，不删除机场订阅、无关代理组和 DNS 配置。
7. 固定出口需求下，不把 DIRECT 或不同出口悄悄加入自动回退。若只是中转回退且落地不变，也要测完整链路；节点自身健康检查不证明链路可用。

“先配好，等会切换”交付候选文件及切换入口即可，记录未启用。只有实际切换后再报告新出口已生效。
